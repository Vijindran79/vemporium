Pay down the verification debt: real migrations + integration suite

Until now not one line of code that writes to a database had ever run. The
entire standard of proof was "tsc passes and it 503s when Postgres is missing".
That is how a broken sign-in shipped as working in an earlier round.

1. Real migration history (prisma migrate dev, not db push)

   prisma/migrations/20261002151840_init/migration.sql is now the baseline.
   Verified against information_schema that sessionVersion, paidAt,
   checkoutTokenHash, fittingSnapshot (jsonb) and every DispatchOutbox column
   actually exist rather than merely appearing in the schema file.

   db push applies a schema without recording it, so there was no way to replay,
   audit or roll back any of it. db:migrate is the documented path now.

2. Prisma 5.22 -> 6.19.3

   prisma@latest resolved to an 8.0 RELEASE CANDIDATE while @prisma/client@latest
   was 7.10 — mismatched, and not something to put in a production tree. Pinned
   both to stable 6.19.3. Upgrade warnings gone; build still clean.

3. Integration suite: 18 tests against live Postgres

   Covers what had never executed:
   - credentials: register, sign in, wrong password vs unknown account are
     indistinguishable, hashes are salted, sessionVersion starts at 0
   - fittingSnapshot survives a jsonb round trip and does NOT follow the
     profile when measurements change afterwards
   - markPaidAndFulfil: PAID, paidAt stamped, stock decremented, outbox row
     queued; REPLAYED THREE TIMES it does not decrement stock again and does
     not queue a second alert — the double-counting bug, now actually proven
   - stock cannot go negative when an order exceeds on-hand, and a paid order
     stays PAID anyway
   - outbox: claimed once and never re-sent; a not-yet-due row is left alone;
     an ORPHANED PROCESSING lock is reclaimed; a FRESH lock is not stolen
   - GDPR erasure against real foreign keys: order re-parented to a tombstone,
     fittingSnapshot and guestEmail nulled, financial record intact, no FK error
   - orderAccessWhere: the owner sees the order, another signed-in user does
     not, an anonymous caller does not

4. Live sign-in over HTTP, end to end

   CSRF -> POST /api/auth/callback/credentials -> 302 -> authjs.session-token.
   Then GET /api/avatars returned 200 {"avatars":[]} — real session data, not a
   401. Then bumped sessionVersion in the database and reused the SAME cookie:
   401 {"error":"Not signed in"}.

   That is the exact security property claimed when JWT sessions replaced
   database sessions, now demonstrated rather than asserted. It is the check
   whose absence let the broken credential config ship unnoticed before.

Also: dev.log had been committed by accident; now gitignored and untracked.
