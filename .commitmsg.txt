Stripe Elements + confirmation screen

PaymentElement mounts on a fourth checkout step, rendering whatever methods
Stripe enables for the intent. confirmPayment uses redirect: 'if_required', so a
card settles in place with no navigation; redirect methods still leave for the
provider and come back to /orders/[id]/confirmation.

The confirmation screen polls because it has to. The shopper usually arrives
BEFORE the webhook has run — Stripe redirects the instant payment succeeds and
the signed webhook is a separate request seconds behind. PENDING_PAYMENT on
arrival is the normal case for a successful payment, so it renders as "payment
processing, this page updates itself" rather than an error. Backoff, stops on
terminal status, hard stop at the cap so a backgrounded tab stops hammering the
API. Polling over SSE/WebSockets because this is a serverless deployment and a
long-lived connection is a poor trade for one status field.

The checkout token is NOT in the URL

The spec had return_url pointing at ?token=[checkoutToken]. Undone deliberately:
return_url carries only the order id, the token lives in sessionStorage, and it
travels as an x-checkout-token header. A bearer credential in a query string
lands in browser history, in the Referer header sent to every third-party script
on the confirmation page, in access logs and in analytics. sessionStorage is also
tab-scoped and self-clearing, which suits a credential that authorises exactly
one checkout attempt.

One authorisation rule for two endpoints

orderAccessWhere() returns a Prisma `where` predicate rather than doing a fetch,
so the security rule is unit tested without a database — it is a boundary, not an
integration detail. /api/checkout/create-intent and the new GET /api/orders/[id]
both use it, so "can I pay for this order" and "can I look at this order" cannot
drift apart. A session takes precedence over a token, so a signed-in shopper
presenting someone else's token is still scoped to their own orders. create-intent
no longer accepts a token in the request body at all.

Degrades honestly without configuration: no NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY
renders an explicit "payments not configured" panel, and the order is left
PENDING_PAYMENT rather than marked paid.

Two SDK mismatches worth recording: this version's Elements has no onReady prop
and types elements.on only for 'update-end', so PaymentElement readiness uses a
narrow documented cast. And money() from MoneyProvider takes a USD base and
re-converts — wrong for stored order totals, and wrong when the shopper's current
market differs from the order's currency, so the confirmation screen formats via
formatMoney(amount, orderCurrency) instead.

Verified live: confirmation page 200, /api/orders/[id] and create-intent both
503 when the database is down rather than 500ing, checkout renders without a
publishable key, and a body-supplied checkoutToken is ignored.
