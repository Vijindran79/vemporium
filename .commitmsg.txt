Link orders to the session before payment capture

Orders are resolved against the session inside POST /api/orders, so when the
Stripe intent succeeds the webhook transitions an order that already has an
owner. Capturing first means reconciling orphan guest orders afterwards,
against a customer who is already asking where their order went.

- userId comes from the session, never the body. A client-supplied userId would
  let anyone write orders into someone else's history
- guest checkout still works, but requires an email. An order with no owner and
  no email could never be delivered or refunded, only lost
- idempotencyKey is client-supplied and stable per checkout ATTEMPT, so a
  double-clicked "Place order" returns the original order rather than creating a
  second one that gets charged twice. The unique constraint is the real guard;
  a P2002 race resolves to the winning order instead of a 500

fittingSnapshot freezes measurements at purchase

Order.fittingSnapshot JSON, not a foreign key. The shopper edits their profile
next month; a return three months after that would otherwise be judged against
the wrong body, and the blame would land on the customer for our bug.

Measured against that: it stores measurements only. No skin tone, no hair,
because this column outlives the account it came from — and erasure now scrubs
it. Tax law requires the transaction, not the customer's waist.

FIX: sign-in was broken and shipped that way

Configured with session.strategy "database" and the Credentials provider.
Auth.js refuses that pairing outright (@auth/core/lib/utils/assert.js:
"Signing in with credentials only supported if JWT strategy is enabled").

The config parsed, tsc passed, the build passed, and every login failed at
runtime. Nothing in the toolchain could have caught it.

Now JWT, with the revocation that database sessions would have given us
recovered via User.sessionVersion: the session callback re-reads the user on
every request and drops the session if the account is gone or the version
moved. So erasure still signs the shopper out immediately rather than at token
expiry, which was the actual requirement.

SESSION_STRATEGY is a named constant with a test, so this cannot silently
regress again. Verified UnsupportedStrategy occurrences in the runtime log went
5 -> 0.

Also: preflight DB reads are now inside the error boundary, so an unreachable
database returns 503 instead of an unhandled 500 leaking a Prisma stack trace.

64 tests (was 58), tsc clean, 20 routes build clean.
