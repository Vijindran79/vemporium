Stripe capture: one path to PAID, notifications out of the transaction

The state machine in the spec is right, but step 4 — dispatching supplier
WhatsApp alerts inside prisma.$transaction — is wrong in both directions:

  - send, then roll back -> a karigah has been told to start work on an order
    that does not exist
  - commit, then the send fails -> the customer paid and nobody told the
    workshop, so the order rots in PENDING_PAYMENT forever

Neither recovers automatically. So the transaction records INTENT (status,
stock, a DispatchOutbox row) and returns; messages go out afterwards. A failed
dispatch leaves the row FAILED for a retry sweep and never un-pays an order.
The trade is deliberate: at-least-once notification in exchange for never
telling a supplier about a rolled-back order.

- Stripe webhook: raw body, signature verified before parsing, no dev-mode
  bypass. An unauthenticated payment webhook is a free order-press, so unlike
  the legacy internal one it refuses everything when the secret is absent
- transition guarded by a conditional updateMany on status === PENDING_PAYMENT,
  so concurrent retries race on the row lock and exactly one wins
- stock decremented conditionally (stockLevel >= qty) so two orders racing for
  the last unit cannot drive it negative. A shortfall is recorded but does NOT
  block fulfilment: the money is captured, and refusing would be the worse
  outcome
- only payment_intent.succeeded fulfils. payment_intent.payment_failed is also
  handled, and deliberately only CANCELS — without it, abandoned checkouts sit
  in PENDING_PAYMENT forever. It cannot cause a double fulfilment.

create-intent is authorised, which the spec omitted

{ orderId } with no ownership check means any signed-in shopper can attach a
payment intent to someone else's order, and since ids are enumerable, read their
basket and total. The order must belong to the session, or the caller must
present the one-time checkoutToken minted at creation (guests have no session to
check against). Both failures return 404, because distinguishing "not yours"
from "does not exist" is itself the leak.

The amount always comes from the persisted Order.totalLocal. A client-supplied
amount is a client-supplied price.

Consolidated toMinorUnits

payments.ts already had toMinorUnits(amount, zeroDecimal: boolean), and I wrote
a second one taking a currency code. That boolean is the trap: pass false for a
JPY order and you charge 100x. The code is always in hand at the call site, so
the boolean version is deleted and callers updated. Also covers the display path,
which was using the provider's zeroDecimal flag as if it were a property of the
money.

Also fixed while verifying: create-intent and the legacy webhook both 500'd on
an unreachable database instead of degrading to 503, and the legacy webhook
validated status only after touching the DB — so order.status_changed with
status PAID was reachable. Validation now runs before any DB work.

Verified live: forged stripe signature -> 400, missing signature -> 400,
order.created and order.paid on the legacy endpoint -> 410, status PAID via
order.status_changed -> 400, unauthenticated create-intent -> 503.
